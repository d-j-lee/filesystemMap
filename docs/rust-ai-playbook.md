# Rust × AI 실전 플레이북

> 대상: AI 코딩 에이전트를 이미 적극적으로 쓰는 시니어 개발자.
> 근거 자료는 [research/rust-ai-evidence-2026-10.md](research/rust-ai-evidence-2026-10.md)와 [보충 자료](research/rust-ai-evidence-addendum-2026-10-28.md)에 출처·날짜와 함께 정리했습니다. 출처 없이 적힌 판단은 "경험칙"으로 표시했습니다.
> 이 문서는 주장만 하지 않고, 같은 방법으로 만든 이 저장소(`fsmap`)에서 실제로 잰 결과도 같이 적습니다.

## 1. 핵심 명제

**AI가 줄인 것은 Rust의 *학습 비용*이고, *검증·소유 비용*은 그대로입니다. 그래서 컴파일러가 검증의 상당 부분을 대신하는 Rust가 AI와 특히 잘 맞습니다.**

- AI의 전형적인 실패는 "그럴듯하지만 틀린 코드"입니다. 동적 언어에서는 이것이 런타임까지, 즉 리뷰어의 눈까지 넘어옵니다. Rust에서는 상당수(타입·소유권·수명·스레드 안전성)가 **컴파일 에러로 바뀌어** 에이전트에게 즉시 되돌아갑니다.
- 그 결과 에이전트가 사람 개입 없이 돌 수 있는 루프가 길어집니다. Bun 팀이 Zig 53만 줄을 11일 만에 Rust로 옮기며 남긴 말이 요약입니다: *"Compiler errors are a better feedback loop than a style guide."* (자체 보고, 근거 문서 §4)
- 연구 결과도 같은 방향입니다. 컴파일러 피드백을 반복 입력하면 실제 Rust 컴파일 에러를 약 74% 고칩니다(RustAssistant). C→Rust 번역 벤치마크(CRUST-Bench)에서는 단발 생성(o1)이 15%, 컴파일·테스트 반복 루프(o3)가 48%를 통과했습니다. 다만 모델이 서로 달라서 루프만의 효과를 분리한 수치는 아닙니다.

반대 근거도 분명합니다. 이것을 알고 쓰는 것이 이 플레이북의 목적입니다.

| AI × Rust의 약점 | 근거 | 대응 (§4) |
|---|---|---|
| 존재하지 않는 크레이트·API를 지어냄 | 패키지 환각률: Rust 24.7%, Python 23.1%, JS 14.7% | `cargo add`로만 추가, 로컬 레지스트리 소스를 근거로 사용 |
| 학습 시점 이후의 API 변경에 약함 | 컷오프 이후 API 성공률 32.5% (이전은 56.1%) | 버전 고정, 실제 해석된 소스를 읽게 함 |
| 컴파일이 느려 루프가 길어짐 | 사용자의 27.3%가 "큰 문제"로 꼽음 | `cargo check` 중심 루프, 릴리스 빌드는 마지막에만 |
| 컴파일을 통과시키려고 꼼수를 씀 | Bun: "크레이트를 컴파일되게 하자"를 "에러 나는 함수를 스텁으로 비우자"로 해석 | `todo!()`·`unimplemented!()`는 lint로 deny, `#[allow]`와 긴 변명 주석은 리뷰에서 근거를 요구 (§4.3) |
| 컴파일러는 로직 오류를 못 잡음 | 이 저장소의 실측 (§6) | 통합 테스트·속성 테스트는 여전히 필수 |

## 2. 현실 지표: 사랑받지만 덜 쓰인다

- Stack Overflow 2026: Rust를 실제로 쓰는 개발자는 **18.0%**(12위)입니다. 써 본 사람 중 계속 쓰고 싶다는 비율(admired)은 67.4%입니다.
- 2025년에는 admired 72.4%, 사용률 14.8%였습니다. **좋아하는 비율과 쓰는 비율의 격차**가 곧 도입 비용입니다. AI가 압축하는 것도 정확히 이 부분입니다.
- 큰 흐름은 이미 정해졌습니다.
  - Android: 메모리 안전 취약점 비중이 처음으로 20% 아래로 내려갔습니다. 100만 줄당 취약점 밀도는 Rust ≈0.2, C/C++ ≈1,000입니다. Rust 변경은 롤백이 약 4배 적고 리뷰 시간이 약 25% 짧습니다.
  - Linux 커널: Rust가 "더 이상 실험이 아니다"로 정리됐습니다.
  - Git: 3.0에서 Rust를 필수로 만들 계획입니다.
- **Chromium**(이 프로젝트의 출발점)도 이미 Rust를 들이고 있습니다.
  - 폰트 스택(Fontations)이 들어오면서 Blink에서 FreeType이 제거됐습니다.
  - JSON 파서와 PNG 디코더가 Rust로 교체됐습니다.
  - 2026년에는 Site Isolation 정책 코드까지 Rust로 옮기는 실험이 진행 중입니다.
  - 배경에는 Chromium의 "Rule of 2"가 있습니다. 신뢰할 수 없는 입력, 안전하지 않은 구현 언어, 높은 권한 중 **둘까지만** 허용한다는 규칙입니다. 메모리 안전 언어로 쓰면 이 중 하나가 빠지기 때문에, 교체 대상도 JSON·PNG·폰트처럼 외부 입력을 해석하는 코드부터였습니다.

## 3. 어디에 Rust를 쓸 것인가 (의사결정 기준)

| 상황 | 판단 | 이유 |
|---|---|---|
| 사내 CLI·개발 도구·에이전트용 도구 | **강력 추천** | 단일 정적 바이너리라 배포가 끝납니다. 병렬 I/O가 빠르고, 실패해도 범위가 작습니다. 이 저장소가 그 예입니다. |
| Python/Node 서비스의 핫패스 | **추천 (점진적 교체)** | PyO3+maturin, napi-rs로 함수 하나부터 바꾸고 전후를 측정합니다. Polars, pydantic-core, ruff가 이미 이렇게 만들어졌습니다. |
| 외부 입력을 파싱하는 코드 (파일 포맷, 프로토콜) | **추천** | Chromium의 "Rule of 2"와 같은 논리입니다(§2). 메모리 안전성이 곧 보안입니다. |
| 브라우저·엣지에서 도는 연산 | 조건부 | wasm-bindgen으로 갈 수 있지만, JS와 데이터를 주고받는 비용이 이득을 상쇄하기 쉽습니다. 경계 비용부터 측정하세요(경험칙). |
| 기존 대형 코드베이스의 "포팅" | 신중 | TypeScript 컴파일러는 Go를 택했습니다. 구조를 그대로 옮기는 *포팅*에서는 순환 참조가 많은 그래프와 GC 의존 설계가 Rust와 충돌합니다. 재설계할 생각이 없다면 Go/Kotlin이 더 맞을 수 있습니다. |
| 빠른 UI 프로토타입, ML 학습 코드 | 비추천 | 생태계와 반복 속도에서 Python/TS가 압도적입니다. |
| 팀에 Rust 리뷰어가 0명 | 보류 | AI가 쓴 코드를 아무도 판정하지 못합니다. 리뷰어 1명을 먼저 확보하세요. |

## 4. AI와 Rust를 함께 쓰는 작업 루프

### 4.1 피드백 사다리: 싸고 빠른 것부터

```
cargo check                      # 초 단위. 에이전트의 기본 루프
cargo clippy --all-targets -- -D warnings
cargo test                       # 또는 cargo nextest run
cargo +nightly miri test         # unsafe가 있을 때만
cargo fuzz run <target>          # 외부 입력 파서에
cargo deny check                 # 라이선스·취약 크레이트·중복 버전
```

에이전트에게 "**`cargo check`가 깨끗해질 때까지 스스로 고치고, 그다음 clippy, 그다음 test**" 순서를 명시하면 루프가 안정적으로 수렴합니다. 이 저장소의 [CLAUDE.md](../CLAUDE.md)가 그대로 쓰는 예시입니다.

### 4.2 환각 차단: "근거는 디스크에 있다"

- 의존성은 반드시 `cargo add <crate>`로 추가하게 하세요. 그러면 최신 호환 버전이 `Cargo.toml`에 고정되고, 에이전트가 지어낸 버전 번호가 들어갈 틈이 없습니다.
- 크레이트 API가 헷갈리면 **실제로 해석된 소스**를 읽게 하세요. 그 소스는 `~/.cargo/registry/src/*/<crate>-<version>/`에 있습니다. 학습 데이터보다 정확하고, 오프라인에서도 됩니다. docs.rs는 그다음입니다.
- Claude Code에 공식 `rust-analyzer-lsp` 플러그인을 설치하면 정의로 이동, 참조 찾기, 진단을 에이전트가 직접 씁니다. rust-analyzer 바이너리는 따로 설치해야 합니다.

### 4.3 꼼수 차단: 컴파일만 되는 코드를 막는 장치

`Cargo.toml`에 넣습니다:

```toml
[lints.rust]
unsafe_code = "forbid"          # 필요한 모듈만 예외로 열기

[lints.clippy]
todo = "deny"
unimplemented = "deny"
dbg_macro = "deny"
```

- 리뷰에서 볼 신호는 다음과 같습니다. 빌림 검사기를 피하려고 넣은 `.clone()`, 근거 없는 `.unwrap()`, 늘어나는 `#[allow(...)]`, 함수 시그니처에 붙은 `'static`.
- 타입을 명세로 쓰세요. 상태는 `enum`으로, 단위가 있는 값은 newtype으로 만들면 AI가 틀릴 공간이 줄어듭니다.

### 4.4 컴파일 시간 관리

- 루프는 `cargo check`로 돌리고, `--release`는 마지막 측정 때만 씁니다.
- 링크 시간이 병목이면 `mold`/`lld`, 반복 빌드가 많으면 `sccache`를 씁니다.
- 크레이트를 너무 이르게 쪼개지 마세요. 워크스페이스 분할은 두 번째 프론트엔드가 생길 때 합니다(이 저장소의 D-01).

### 4.5 "AI로 Rust 배우기"를 넘어 "AI가 쓴 Rust를 판정하기"

시니어에게 필요한 것은 문법이 아니라 **판정 능력**입니다. 다음 다섯 가지면 대부분의 리뷰가 가능합니다.

1. 소유권 이동과 빌림 (`&`, `&mut`, 이동 후 사용 금지)
2. 수명 생략 규칙: 시그니처에 수명이 보이면 왜 필요한지 물어볼 것
3. `Send`/`Sync`: 무엇이 스레드를 넘어가는가
4. 에러 전략: 라이브러리는 `thiserror`, 애플리케이션은 `anyhow`
5. async의 비용: 필요할 때만 쓰고, 이 저장소처럼 동기 + rayon으로 충분한 경우가 많습니다

컴파일 에러가 나면 에이전트에게 "**이 에러를 소유권 관점에서 한 문장으로 설명해**"라고 시키세요. `rustc --explain E0502`와 같이 보면 리뷰 감각이 빠르게 붙습니다(경험칙: 몇 주 단위).

## 5. 도입 로드맵 (개인 → 팀)

| 시점 | 할 일 | 성공 기준 |
|---|---|---|
| 1~2주 | AI와 개인용 CLI 도구 하나 완성 (예: 이 저장소) | CI 녹색, 실제 업무에 사용 |
| 1개월 | 기존 Python/Node 서비스의 핫패스 1개를 PyO3/napi-rs로 교체 | 전후 지연·메모리 측정치 |
| 분기 | 사내 배포용 단일 바이너리 + clippy/test/deny CI 템플릿 | 템플릿 재사용 2건 이상 |
| 팀 | `unsafe` 정책, 크레이트 허용목록(cargo-deny), "서드파티 크레이트 먼저, C++→Rust 단방향 FFI"로 시작 (Chromium의 2023년 출발점. 지금은 1st-party Rust와 양방향 interop까지 넓어짐) | 리뷰 가이드 문서화 |

## 6. 이 저장소에서 실제로 해 본 것

같은 방법으로 `fsmap`을 만들었습니다. 수치는 이 세션의 도구 실행 결과입니다(2026-10-28, 4코어 클라우드 컨테이너).

- **규모**: Rust 약 9,800줄(테스트 포함)과 뷰어 JavaScript 약 1,000줄. fsmap이 자기 자신을 잰 값입니다(`fsmap scan . | jq .totals.byLanguage`, 2026-10-28). `unsafe`는 0줄이며 `#![forbid(unsafe_code)]`로 막았습니다.
- **성능**:
  - ripgrep 저장소 분석(2,241커밋 전체 이력, 임포트 그래프, 핫스팟)이 0.23초 걸렸습니다(5회 중앙값).
  - `/usr` 93k 노드는 디렉터리 순회 0.14초, 피크 RSS 88MB였습니다.
  - 같은 `/usr`에서 텍스트 456MiB 읽기는 캐시가 따뜻할 때 1.6초, 콜드 캐시에서는 10.8초(I/O 바운드)였습니다.
- **컴파일러가 잡은 것**: 반복 가능한 빌림 충돌(E0502)이 3건 있었고, 그중 하나는 `&mut` 인덱싱 중의 불변 빌림이었습니다. 불안정 API 사용 시도(E0658)도 1건 있었습니다. 모두 실행 전에 차단됐습니다.
- **컴파일러가 못 잡은 것**: 이력 분석 기간을 "현재 시각 기준 2년"으로 잡은 설계 결함이 있었습니다. 2년 넘게 커밋이 없는 저장소는 이력이 통째로 사라집니다. **git 픽스처 위에서 바이너리를 직접 돌리는 통합 테스트**가 이것을 잡았고, 기간을 "저장소의 최신 커밋 기준"으로 바꿨습니다(D-09). 정규식의 탐욕적 매칭 버그(Java 와일드카드 import)는 단위 테스트가 잡았습니다.
- **교훈**: 컴파일러는 *형태*의 오류를 거의 다 잡습니다. *의미*의 오류는 여전히 테스트와 실데이터 검증의 몫입니다. 그래서 실제 OSS 저장소(ripgrep, flask, hono, redis)에 돌려 보고, 결과를 하나씩 원본과 대조했습니다.
  - 예: flask에서 처음 보고된 15개 모듈 순환은 `TYPE_CHECKING` 블록 안의 import였습니다. 런타임 순환이 아닌 오탐이었고, 지연 import를 순환 판정에서 제외하도록 고쳤습니다.
- **독립 리뷰가 잡은 것**: 작성자와 컨텍스트를 공유하지 않는 에이전트에게 세 번 검토를 맡겼습니다(설계 D-08, 코드 D-13, 문서 D-14).
  - 코드 리뷰는 신뢰할 수 없는 저장소의 git filter 설정이 스캔 중 실행될 수 있다는 보안 결함을 찾았습니다. 컴파일러도, 테스트도, 작성자도 놓친 것입니다.
  - 문서 리뷰는 문서와 실제 동작이 어긋난 곳 26군데를 찾았습니다. 그 과정에서 `src/deps/`를 외부 코드로 오분류하는 코드 결함도 하나 드러났습니다.
  - 교훈: AI가 쓴 코드는 AI에게 다시 검토시키되, **반드시 컨텍스트를 끊고 적대적으로** 시키세요.

## 7. 초안(Gemini) 아이디어에 대한 교정

| 초안의 주장 | 교정 |
|---|---|
| Chromium은 gclient/depot_tools 없이는 받기 어렵다 | **빌드**에는 맞습니다. 하지만 **분석**만 하려면 `git clone --filter=blob:none` + sparse-checkout으로 충분합니다. fsmap은 부분 클론을 감지하면 이름 변경을 객체 id가 같은 경우(`-M100%`)로만 추적해서, 이력 분석 중에 blob을 받지 않습니다(D-08, D-13). |
| AST 파서로 의존성을 시각화한다 | AST는 *추출*만 해 줍니다. 진짜 어려운 부분은 *해석*입니다. `use crate::a::b`, `from ..x import y`, tsconfig 경로 별칭, 워크스페이스 패키지가 어느 파일인지 찾아야 합니다. fsmap은 해석에 공을 들였고, tree-sitter는 추출기 교체 경로로 남겨 두었습니다(D-04). |
| 5,100만 줄이 유지되는 비결은 모듈화와 의존성 관리 → 시각화 도구 | 시각화는 출발점일 뿐입니다. Chromium을 지탱하는 것은 디렉터리별 `DEPS` 파일의 include 규칙과 이를 검사하는 checkdeps, 필수 코드 리뷰와 OWNERS 같은 **래칫(ratchet)**입니다. fsmap의 `insights --baseline --fail-on`이 이 아이디어의 경량판입니다. *새로* 생긴 순환·문제만 CI에서 막습니다. |
| ① AI 에이전트용 경량 임베디드 브라우저 | Playwright MCP 같은 CDP·Playwright 기반 도구가 이미 그 자리를 채우고 있습니다. Chromium 래퍼를 직접 유지하면 차별점은 작고 유지비는 큽니다(판단). 꼭 한다면 Rust CDP 클라이언트(chromiumoxide)로 *자동화 계층*만 만드세요. |
