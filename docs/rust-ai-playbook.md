## 1. 핵심 명제

**AI가 줄인 것은 Rust를 *쓰는* 비용이고, 남는 비용은 그 코드가 맞는지 *확인하는* 쪽으로 옮겨갑니다. Rust는 그 확인의 큰 부분을 컴파일러가 강제하는 언어라서 AI와 특히 잘 맞습니다.** (판단)

- AI의 전형적인 실패는 "그럴듯하지만 틀린 코드"입니다. 동적 언어에서는 이것이 런타임까지, 즉 리뷰어의 눈까지 넘어옵니다. Rust에서는 상당수(타입·소유권·수명·스레드 안전성)가 **컴파일 에러로 바뀌어** 에이전트에게 바로 돌아갑니다.
- Bun 팀은 Zig 53만 줄을 11일 만에 Rust로 옮긴 뒤 이렇게 정리했습니다: *"Compiler errors are a better feedback loop than a style guide."* (자체 보고. Bun은 Anthropic 소유)
- 연구도 같은 방향이고, 무엇이 무엇을 올리는지까지 나뉩니다.
  - **같은 모델(o3)** 로 C→safe Rust 번역(CRUST-Bench)을 했을 때 결과는 이렇습니다.

    | 방식 | 빌드 성공 | 테스트 통과 |
    |---|---|---|
    | 한 번에 생성 | 35% | 19% |
    | + 컴파일 에러로 3회 수정 | 68% | 31% |
    | + 테스트 실패로 3회 수정 | 63% | 48% |

    컴파일러 피드백은 주로 *빌드*를 올리고, *정답*을 올리는 것은 테스트 피드백입니다. 둘을 합치면 테스트 통과율이 약 2.5배가 됩니다.
  - 7개 모델이 저장소 단위 Rust 과제를 풀 때, 생성 뒤 컴파일러 피드백을 주면 컴파일 실패율이 평균 65.9%에서 20.7%로, 생성 *중*에 주면 13.1%로 떨어졌습니다(Generative Compilation, 2026-07).
  - 컴파일러 피드백을 반복 입력해 실제 Rust 컴파일 에러를 최고 약 74% 고쳤습니다(RustAssistant). GPT-4 시절 결과이고, 컴파일되게 만든 비율이지 동작이 맞다는 뜻은 아닙니다.
- 그래서 할 일은 **컴파일러 루프와 테스트 루프를 둘 다 에이전트 안에 넣는 것**입니다. 이 저장소의 하네스(§6)가 그 구성입니다.

반대 근거도 분명합니다. 이것을 알고 쓰는 것이 이 플레이북의 목적입니다.

| AI × Rust의 약점 | 근거 | 대응 |
|---|---|---|
| 존재하지 않는 크레이트·API를 지어냄 | 패키지 환각률 Rust 24.7%, Python 23.1%, JS 14.7% | `cargo add`로만 추가, 잠긴 버전의 레지스트리 소스를 근거로 (§5.2) |
| 학습 이후 바뀐 API에 약함 | RustEvo²: 학습 시점 이전 API 56.1%, 이후 32.5%. 검색 보강은 이후 API에서 34.9% → 48.4%. 시그니처는 같고 동작만 바뀐 API는 38.0% | 세션 시작 때 실제 툴체인과 소스 경로를 주입 (§6) |
| 저장소 전체 구조를 놓침 | 저장소 단위 이슈 해결(ICSE 2026): 컴파일 에러의 43.7%가 저장소 구조, 32.6%가 타입·트레이트 규칙에서 | fsmap `context`/`brief`로 구조와 같이 바뀌는 파일을 알려줌 |
| 컴파일을 통과시키려고 꼼수를 씀 | Bun: "크레이트를 컴파일되게 하자"를 "에러 나는 함수를 스텁으로 비우자"로 해석. clippy 도움말도 `#[allow]`를 권함(clippy 1.97에서 확인) | lint 정책 + 통과 시 억제 추가를 사용자에게 보고 (§5.3) |
| 컴파일이 느려 루프가 길어짐 | 사용자의 27.3%가 "큰 문제"로 꼽음 | 편집 직후엔 `cargo check`만, 테스트는 턴 끝에 한 번 (§5.4) |
| 컴파일러는 로직 오류와 누수를 못 잡음 | 이 저장소의 D-09, C 작업의 `Box::leak` 사례 (§8) | 통합 테스트·속성 테스트·적대적 리뷰 |

## 2. 현실 지표: 쓰는 곳은 늘고, 체감은 더디다

- **개발자 전체**: Stack Overflow 2026에서 Rust를 실제로 쓰는 개발자는 **18.0%**(12위)이고, 써 본 사람 중 계속 쓰고 싶다는 비율(admired)은 67.4%입니다. 2025년에는 72.4%와 14.8%였습니다. 좋아하는 비율과 쓰는 비율의 격차가 도입 비용이고, AI가 압축하는 것도 이 부분입니다(판단).
- **Rust 사용자 쪽**: 2025 State of Rust 설문(응답 7,156건)에서 "소속 조직이 Rust를 의미 있게 쓴다"는 응답이 48.8%였습니다(2023년 38.7%, 2024년 45.5%). 응답자 대부분이 이미 Rust 사용자이므로 "기업의 절반"으로 읽으면 안 됩니다. 가장 큰 걱정은 "업계에서 충분히 쓰이지 않는다"(42.1%)와 "언어가 너무 복잡해진다"(41.6%)였습니다.
- **큰 흐름**:
  - **Android**
    - 메모리 안전 취약점 비중이 처음으로 20% 아래로 내려갔습니다.
    - 2025년 1~3분기 자체 플랫폼 코드에서 Rust의 순증 줄 수(추가 − 삭제)가 C++를 약간 넘었습니다.
    - 취약점 밀도는 100만 줄당 Rust 약 0.2, C/C++ 약 1,000입니다. 다만 Rust 쪽은 약 500만 줄에서 잠재 취약점 1건을 찾은 추정치입니다.
    - Rust 변경은 롤백이 약 4배 적고 리뷰 시간이 약 25% 짧습니다. 리뷰 시간 단축은 Google 스스로 팀의 숙련도 상승 덕일 수 있다고 봅니다.
  - **Linux 커널**: 2025년 12월 Maintainers Summit에서 Rust 실험을 끝내고 계속 쓰기로 했습니다. `CONFIG_RUST`는 아직 기본으로 꺼져 있습니다.
  - **Git**: 2.49부터 Rust를 선택적으로 쓸 수 있습니다. 2.55에서 기본, 3.0에서 필수로 만들 계획인데 늦어질 수 있습니다.
- **Chromium**(이 프로젝트의 출발점)도 이미 Rust를 들이고 있습니다.
  - 폰트 스택(Fontations)이 들어오면서 Blink에서 FreeType이 제거됐습니다. JSON 파서와 PNG 디코더도 Rust로 교체됐고, 2026년에는 Site Isolation 정책 코드를 옮기는 실험이 진행 중입니다.
  - 배경에는 "Rule of 2"가 있습니다. 신뢰할 수 없는 입력, 안전하지 않은 구현 언어, 높은 권한 중 **둘까지만** 허용한다는 규칙입니다. 메모리 안전 언어로 쓰면 하나가 빠지므로, 교체도 외부 입력을 해석하는 코드부터였습니다.
- **반례**:
  - TypeScript 컴파일러는 Go로 옮겼습니다. 재작성이 아니라 구조를 그대로 옮기는 *포팅*이었고, GC 전제 설계가 Go와 맞았습니다.
  - Ladybird는 2024년에 Rust를 거부했다가 2026년에 도입했습니다.

## 3. 왜 맞물리는가: 결함이 어디서 잡히나

AI가 쓴 코드에서 "컴파일" 칸의 결함은 사람이 보기 전에 에이전트의 편집 루프 안에서 드러납니다. 다만 에이전트가 그 에러를 `unwrap`, `clone`, `_` 와일드카드로 덮을 수 있어서 린트와 리뷰가 함께 있어야 의미가 있습니다.

| 결함 부류 | Python | TypeScript | Java | C++ | Rust |
|---|---|---|---|---|---|
| 없는 값 참조 | 런타임 | 컴파일(strictNullChecks) | 런타임(NPE) | 미정의 동작 | 컴파일(`Option`), `unwrap`은 런타임 panic |
| 해제 후 사용·이중 해제 | 해당 없음(GC) | 해당 없음(GC) | 해당 없음(GC) | 미정의 동작 | 컴파일(소유권·수명) |
| 데이터 레이스 | 런타임 | 드묾(비동기 경쟁은 흔함) | 런타임 | 미정의 동작 | 컴파일(`Send`/`Sync`). 경쟁 조건·교착은 못 잡음 |
| 순회 중 컬렉션 변경 | 런타임 | 조용한 버그 | 런타임 | 미정의 동작 | 컴파일(빌림 규칙) |
| 처리하지 않은 오류 | 런타임 | 런타임 | 컴파일(checked 예외만) | 경고(`[[nodiscard]]`) | 경고(`must_use`). `let _ =`, `.ok()`는 조용히 버림 |
| 새 상태의 누락된 분기 | 런타임 | 컴파일(never 검사) | 컴파일(sealed + switch) | 경고(`-Wswitch`) | 컴파일(`match` 완전성). `_`가 없을 때만 |

일반적인 언어 특성을 요약한 표입니다(판단). 도구와 설정에 따라 칸이 달라지고, 엄격하게 쓴 TypeScript·Kotlin·Go와의 차이는 표보다 작습니다. Rust도 `unsafe` 안, 논리 오류, 경쟁 조건, 성능 문제는 잡지 못합니다.

**검증 스택.** 위층일수록 싸고 빠르고 자동입니다. 사람에게는 맨 아래 판단만 남기는 것이 목표입니다. 오른쪽 열은 이 저장소의 하네스가 각 층을 언제 돌리는지입니다.

| 층 | 잡는 것 | 언제 |
|---|---|---|
| rustc | 타입, 소유권, 수명, `Send`/`Sync`, 패턴 완전성 | 편집 직후 (`cargo check`) |
| clippy + lint 정책 | `unwrap`, 버려진 에러, 억제 남용, 빌림 회피용 복제 일부 | 턴 종료 시 |
| 테스트·proptest·doctest | 동작, 경계 입력, 성질 | 턴 종료 시, push 전 |
| 소스 열람 | 기억 속 API와 `Cargo.lock` 버전 실제 API의 차이 | 세션 시작 때 경로 주입, API를 쓸 때 |
| 무결성 검사 | 게이트를 무력화하는 cargo·rustfmt 설정과 환경 변수 | 턴 종료 시, push 전 |
| cargo-deny | 알려진 취약점, 라이선스, 출처, 와일드카드 버전 | CI (`--mode full`) |
| rust-reviewer | 별도 서브에이전트의 적대적 리뷰: 빌림 회피 흔적(`clone`·`Arc<Mutex>`·`Box::leak`), 정확성, 동시성, API 실재성 | 큰 변경 마무리 시 |
| 사람 | 타입·모듈 경계, `unsafe`·의존성 승인, 요구사항과의 일치 | 승인 단계 |

clippy는 불필요한 복제를 일부만 잡습니다. C 작업에서는 `&Vec`을 통째로 복제하는 패턴을 놓쳤습니다. 그래서 빌림 회피 판단은 리뷰어 층에 둡니다.

## 4. 어디에 Rust를 쓸 것인가

AI가 작성 비용을 낮춰도 운영·채용·장애 대응 같은 조직 비용은 그대로입니다. 그래서 경계가 좁고, 이득을 숫자로 증명할 수 있고, 실패해도 되돌리기 쉬운 곳부터 시작합니다(판단).

| 상황 | 판단 | 이유 | 시작점 |
|---|---|---|---|
| 개인·사내 CLI, 개발 도구 | **최적** | 단일 정적 바이너리라 배포가 끝납니다. 실패해도 범위가 작고 학습 효과가 큽니다. | `clap` + `anyhow`. 이 저장소가 예 |
| 개인 MCP 서버, 에이전트용 도구 | **최적** | AI를 많이 쓰는 개발자에게 바로 쓸모가 생깁니다. | 공식 Rust SDK `rmcp` (3.8.0, 2026-10-26) |
| Python·Node 서비스의 CPU 핫스팟 | **추천** | 경계가 함수 하나로 좁고 전후 측정으로 증명됩니다. Polars, pydantic-core, ruff가 이렇게 만들어졌습니다. | PyO3 + maturin, napi-rs |
| 외부 입력 파서, 프로토콜 | **추천** | Rule of 2와 같은 논리입니다. 메모리 안전에 proptest·퍼징을 더하면 이득이 가장 큽니다. | proptest, `cargo fuzz` |
| 브라우저·엣지 연산(WASM) | 조건부 | JS와 데이터를 주고받는 비용이 이득을 상쇄하기 쉽습니다. 경계 비용부터 재세요(경험칙). | wasm-bindgen |
| 신규 고성능 네트워크 서비스 | 조건부 | async 복잡도와 운영 역량(관측, 장애 대응)이 필요합니다. | axum + tokio, 작은 내부 서비스부터 |
| 기존 C/C++ 대규모 이식 | 조건부 | 테스트 자산이 전제입니다. 자동 번역은 o3 기준 48%(§1)로 아직 연구 단계에 가깝습니다. Ladybird는 LibJS 2.5만 줄을 AST·바이트코드 동일성과 test262로 검증하며 옮겼습니다. | 모듈 하나를 FFI 경계로 감싸 교체 |
| GC 전제의 대형 코드베이스 *포팅* | 신중 | 순환 참조가 많은 그래프와 GC 의존 설계가 Rust와 충돌합니다. 재설계할 생각이 없다면 Go/Kotlin이 더 맞을 수 있습니다(TypeScript → Go). | — |
| 일반 CRUD 백엔드(JVM·TS 팀) | 비추천 | 성능·안전 이득이 작고 조직 비용이 큽니다. | 기존 스택 유지 |
| ML 연구 코드, UI 중심 프론트 | 비추천 | 생태계와 반복 속도에서 Python·TS가 압도합니다. 핫스팟만 떼어내는 것은 예외입니다. | 위 핫스팟 브리지 |
| 팀에 Rust 리뷰어가 0명 | 보류 | AI가 쓴 코드를 아무도 판정하지 못합니다. 리뷰어 1명을 먼저 확보하세요. | — |

## 5. AI와 Rust를 함께 쓰는 작업 루프

### 5.1 피드백 사다리: 싸고 빠른 것부터

```
cargo check                                  # 초 단위. 에이전트의 기본 루프
cargo clippy --all-targets -- -D warnings
cargo test                                   # 또는 cargo nextest run
cargo +nightly miri test                     # unsafe가 있을 때만
cargo fuzz run <target>                      # 외부 입력 파서에
cargo deny check                             # 라이선스·취약 크레이트·중복 버전
```

에이전트에게 "`cargo check`가 깨끗해질 때까지 스스로 고치고, 그다음 clippy, 그다음 test" 순서를 명시하면 루프가 안정적으로 수렴합니다. 이 순서는 이 저장소의 [CLAUDE.md](../CLAUDE.md)에 그대로 있습니다. 하네스를 쓰면 편집 직후의 `cargo check`와 턴 끝의 나머지(`fsmap verify`)가 자동으로 돕니다.

### 5.2 환각 차단: "근거는 디스크에 있다"

- 의존성은 `cargo add <crate>`로만 추가하게 하세요. 최신 호환 버전이 `Cargo.toml`에 들어가고, 지어낸 버전 번호가 끼어들 틈이 없습니다.
- 크레이트 API가 헷갈리면 **잠긴 버전의 실제 소스**를 읽게 하세요. `~/.cargo/registry/src/*/<crate>-<version>/`에 있고, 학습 데이터보다 정확하며 오프라인에서도 됩니다. 하네스의 세션 시작 훅은 직접 의존성마다 이 경로와 실제 `rustc`/`cargo` 버전을 에이전트에게 알려줍니다.
  - C 작업의 사례: PyO3 0.30.1에는 `allow_threads`가 없습니다. 0.26.0(2025-08-29)에 `detach`로 이름이 바뀌었고 0.28.0(2026-02-01)에 옛 이름이 제거됐습니다. 이름이 바뀐 API는 컴파일러가 잡지만, 시그니처가 같고 동작만 바뀐 API는 조용히 틀립니다. 그래서 소스를 여는 습관이 더 중요해집니다.
- 로컬 Claude Code에서는 공식 `rust-analyzer-lsp` 플러그인으로 정의 이동·참조 찾기·진단을 에이전트가 직접 씁니다. `rust-analyzer` 바이너리는 따로 설치해야 합니다. 클라우드(웹) 세션은 플러그인 언어 서버를 띄우지 않으므로 편집 직후 훅의 `cargo check`가 그 역할을 대신합니다.

### 5.3 꼼수 차단: 컴파일만 되는 코드를 막는 장치

`Cargo.toml`에 넣습니다(이 저장소의 실제 설정):

```toml
[lints.rust]
unsafe_code = "forbid"

[lints.clippy]
todo = "deny"
unimplemented = "deny"
dbg_macro = "deny"
allow_attributes = "warn"                  # 억제는 이유를 단 #[expect]로만
allow_attributes_without_reason = "warn"
unwrap_used = "warn"                       # clippy.toml: allow-unwrap-in-tests = true
map_err_ignore = "warn"                    # 원인 에러를 버리는 map_err(|_| ..)
redundant_clone = "warn"                   # 빌림 검사기를 복제로 피하기
clone_on_ref_ptr = "warn"
```

- 게이트가 `-D warnings`로 돌기 때문에 "warn"도 실패입니다.
- **`#[allow]` 대신 이유를 단 `#[expect]`**를 쓰게 하세요. 억제가 필요 없어지면 컴파일러가 알려주므로 저절로 정리됩니다. clippy 도움말은 "의도한 것이면 `#[allow(...)]`로 허용하라"고 권하는데(clippy 1.97에서 확인), 에이전트가 이를 그대로 따르면 린트가 무력화됩니다.
- 하네스는 게이트를 통과한 변경에 `#[allow]`·`#[expect]`·`#[ignore]`·`#[should_panic]`·`cfg(any())`가 새로 생겼거나 단언이 지워졌으면 사용자에게 보여줍니다. 정당한 억제도 있으므로 막지는 않고, 판단은 사람이 합니다.
- 알아둘 예외들:
  - `allow-unwrap-in-tests`는 통합 테스트 파일의 헬퍼 함수에는 적용되지 않습니다. 이 저장소에서는 crate 수준 `#![expect(clippy::unwrap_used, reason = …)]`로 처리했습니다.
  - 여러 테스트 crate가 공유하는 모듈의 `dead_code`는 crate마다 쓰는 헬퍼가 달라서 `expect`가 성립하지 않습니다. 이런 곳만 이유를 단 `allow`가 맞습니다.
  - `redundant_clone`은 nursery 그룹이라 툴체인에 따라 오탐이 날 수 있습니다. 오탐이 나면 가장 먼저 뺄 린트입니다(D-15).
- **리뷰에서 볼 신호**: 빌림 검사기를 피하려고 넣은 `.clone()`·`Rc<RefCell>`·`Arc<Mutex>`·`Box::leak`, 근거 없는 `.unwrap()`, 시그니처에 붙은 `'static`, 워크어라운드를 정당화하는 긴 주석. Bun 팀이 리뷰어에게 준 기준은 이렇습니다: "워크어라운드가 괜찮은 이유를 설명하려고 한 문단짜리 주석이 필요하다면 코드가 틀린 것이다."
- **타입부터 리뷰하기**: 구현 전에 "타입·트레이트·공개 함수 시그니처만 먼저 제안해"라고 시키고 그 부분만 보세요. 상태는 `enum`, 검증된 값은 newtype으로 만들면 이후 구현의 일관성은 컴파일러가 지킵니다. 리뷰 대상이 수백 줄 구현에서 수십 줄 타입으로 줄어듭니다(판단).

### 5.4 컴파일 시간과 병렬 세션

- 루프는 `cargo check`로 돌리고, `--release`는 마지막 측정 때만 씁니다. 링크가 병목이면 `mold`/`lld`, 반복 빌드가 많으면 `sccache`를 씁니다. `sccache`처럼 `RUSTC_WRAPPER`를 쓰는 도구는 하네스 설정의 `trust`에 명시해야 합니다.
- 크레이트를 너무 일찍 쪼개지 마세요. 워크스페이스 분할은 두 번째 프론트엔드가 생길 때 합니다(이 저장소의 D-01). 참고로 workspace `exclude`는 glob을 처리하지 않습니다(cargo 1.97에서 확인).
- Rust 프로젝트는 2026년 목표로 병렬 프런트엔드, Cranelift 백엔드, "재빌드 대신 재링크", 증분 컴파일 재설계 등을 추진하고 있습니다.
- **병렬 세션이나 worktree에서 빌드 디렉터리를 공유하지 마세요.** C 작업에서는 사본 하나의 산출물로 다른 사본의 검증이 통과했습니다. 하네스는 게이트를 돌릴 때 `CARGO_TARGET_DIR`을 저장소 안으로 강제하고, 같은 worktree에 다른 세션이 있으면 알립니다.

### 5.5 "AI로 Rust 배우기"를 넘어 "AI가 쓴 Rust를 판정하기"

시니어에게 필요한 것은 문법 암기가 아니라 **판정 능력**입니다. 다음 다섯 가지면 대부분의 리뷰가 됩니다.

1. 소유권 이동과 빌림 (`&`, `&mut`, 이동 후 사용 금지)
2. 수명 생략 규칙: 시그니처에 수명이 보이면 왜 필요한지 물어볼 것
3. `Send`/`Sync`: 무엇이 스레드를 넘어가는가
4. 에러 전략: 라이브러리는 `thiserror`, 바이너리는 `anyhow`
5. async의 비용: 필요할 때만 씁니다. 이 저장소처럼 동기 코드 + rayon으로 충분한 경우가 많습니다. async 안의 블로킹 호출, `.await` 너머로 들고 가는 락, 상한 없는 채널은 컴파일되지만 운영에서 터집니다.

| 직접 판단할 것 | 맡겨도 되는 것 |
|---|---|
| 타입·모듈 경계, 소유권을 누가 갖는지 | 보일러플레이트, serde·clap 연결, FFI 글루 |
| 공유 상태와 동시성 구조 | 컴파일 에러 해석과 1차 수정 |
| `unsafe`와 의존성 추가 | 테스트 초안, proptest 전략 |
| 테스트가 무엇을 증명하는지 | 벤치마크와 결과 일치 검증 코드 |

컴파일 에러가 나면 에이전트에게 "이 에러를 소유권 관점에서 한 문장으로 설명해"라고 시키세요. `rustc --explain E0502`와 같이 보면 리뷰 감각이 빠르게 붙습니다(경험칙: 몇 주 단위). `unsafe`는 전역 forbid로 두고, 필요하면 구현 전에 이유·불변식·격리 방법을 제안받아 승인한 뒤 별도 모듈에 `// SAFETY:` 주석과 Miri로 가둡니다.

## 6. 하네스: 검증 층과 맥락 층

에이전트가 일하는 동안 필요한 피드백은 두 종류입니다.

| 층 | 질문 | 제공 |
|---|---|---|
| 검증 | 컴파일되나, 린트·테스트를 통과하나, 통과하려고 검사를 약하게 만들지 않았나 | `fsmap verify`와 Claude Code 훅 |
| 맥락 | 이 저장소는 어떻게 생겼나, 이 파일과 늘 같이 바뀌는 파일은 무엇인가, 어디가 위험한가 | fsmap 분석: `brief`, `context`, `insights` |

C의 `rust-ai-harness`와 A의 템플릿 구상은 검증 층을, fsmap은 맥락 층을 갖고 있었습니다. 지금은 하나의 바이너리가 둘 다 에이전트 루프에 넣습니다(D-15).

| 시점 | 하는 일 | 이 저장소 실측 |
|---|---|---|
| 세션 시작 | 기준점 기록(`startup` 때만), 실제 툴체인과 의존성 소스 경로 주입, 게이트를 약하게 만드는 설정과 다른 세션 경고 | 0.4초 |
| 편집 직후(`.rs`, `Cargo.toml`, `build.rs`) | 편집한 패키지에 `cargo check`. 에러는 차단 사유로, fsmap 브리핑은 맥락으로 전달 | 중앙값 1.1초 |
| 턴 종료 | 트리가 바뀌었으면 `fsmap verify`. 모든 단계가 통과해야만 통과. 실패는 종료를 막고, 3회 연속이면 풀고 "보고하라"고 지시. 실패가 전부 세션이 건드리지 않은 파일에 있으면 한 번만 막은 뒤 보고로 넘김(사용자에게 "통과 아님" 표시) | 37~42초 |
| 사용자 입력 | 실패 연속 횟수 초기화 | 밀리초 |
| `git push`, `gh pr create/merge` 직전 | 이 트리가 통과한 기록이 없으면 게이트를 돌려 실패면 명령 거부. 따옴표·`sh -c`·`env` 같은 감싸기와 git·gh의 전역 옵션까지 읽음 | 다른 명령은 5ms |

**어디서 무엇을 가져왔나.**

- **C에서 유지한 것**
  - 사람·에이전트·CI가 같은 게이트를 씁니다.
  - 편집 직후는 가볍게, 턴 종료는 엄격하게 검사합니다.
  - 3회 막히면 보고를 강제하고 풀어줍니다.
  - 학습 기억보다 현재 환경(실제 툴체인과 소스)을 주입합니다.
  - 하네스 자신을 시험하는 테스트를 둡니다.
  - 적대적 리뷰어 서브에이전트(`rust-reviewer`)를 씁니다.
- **C가 찾은 구멍을 일반화해 막은 것**
  - 턴 중 커밋으로 게이트 통과
  - 도구가 없으면 게이트가 꺼짐
  - `--config` 플래그로 검사 무력화
  - 빌드 디렉터리 공유
  - 빈 저장소의 첫 커밋

  예를 들어 `--config` 하나만 막지 않고, cargo·rustfmt·rustup 설정 파일과 환경 변수 전체를 검사합니다.
- **설계 리뷰에서 새로 나온 것**
  - `.git/info/exclude`로 숨긴 `.cargo/config.toml` 한 줄이 실패하는 테스트를 통과로 바꿨습니다(재현됨). 이것을 막는 무결성 단계를 넣었습니다.
  - 자동 압축(compaction)이 깨진 트리를 기준점으로 다시 기록하던 문제를 막았습니다.
  - 백그라운드 개발 서버가 게이트를 영구히 끄던 문제를 막았습니다.
  - push 전 게이트를 추가했습니다.
  - 억제가 추가되면 사용자에게 보고합니다.
- **구현 리뷰에서 다시 고친 것**: 완성된 하네스를 또 다른 독립 에이전트에게 맡겼더니 차단 2건, 주요 6건이 나왔습니다.
  - 무결성 단계가 설정을 줄 단위로 읽어 우회가 일곱 가지였습니다. `[alias]`로 `cargo clippy` 바꿔치기, 가짜 linker, 문자열 안의 `#`, TOML 이스케이프, 하위 디렉터리의 `rustfmt.toml`, 점 표기 `toolchain.path` 등입니다. 실제 TOML 파서와 **허용 목록**으로 바꾸고, toolchain 파일은 cargo를 처음 실행하기 전에 검사합니다.
  - "세션 전 실패는 보고만" 규칙이 새 실패도 통과시켰습니다. 헬퍼의 유일한 호출을 지우면 건드리지 않은 파일에 dead code가 생깁니다. 이제 게이트는 모든 단계가 통과해야만 통과합니다.
  - cargo가 프로젝트를 못 읽으면 훅이 아무 말 없이 지나갔고, 깨진 커밋으로 시작한 세션은 그 커밋을 push할 수 있었습니다. 둘 다 막았습니다.
  - 그리고 이 문서와 안내서가 코드보다 많이 주장하고 있었습니다(아래 8.1).
- **A의 템플릿 구상**: `harness/` 아래의 설정·`AGENTS.md`·리뷰어 템플릿이 됐습니다. 이 저장소는 그 사본을 쓰고, 사본이 같은지 테스트가 확인합니다.

**도입은 다섯 단계입니다.** 자세한 내용은 [agent-harness.md](agent-harness.md)에 있습니다.

1. fsmap을 설치합니다(`cargo install --locked --git https://github.com/d-j-lee/filesystemMap fsmap`). 클라우드 환경이면 setup script에 넣습니다.
2. `harness/`의 세 파일을 복사합니다.
3. lint와 `deny.toml`을 가져옵니다.
4. 필요하면 `Cargo.toml`에 추가 검사와 `trust`를 적습니다.
5. CI에 `fsmap verify --mode full --strict` 잡을 추가합니다.

첫 세션에서 에이전트 맥락이 `[harness] fsmap … hooks are active`로 시작하면 동작하는 것입니다.

**한계를 알고 쓰세요.**

- **가드레일이지 보안 경계가 아닙니다.** 에이전트는 훅이 읽는 파일을 고칠 수 있습니다. 게이트의 최종 기록은 CI입니다.
- **적용 범위**: 저장소의 훅·권한 규칙은 클라우드에서 *저장소 하나로 연 세션, 프로젝트 스레드 밖*에서만 적용됩니다.
- **신뢰하는 저장소에만 켜세요.** build script·proc macro·테스트가 자동으로 실행됩니다.
- **아직 커버하지 못한 것**: 하위 디렉터리의 워크스페이스, 저장소 밖 path 의존성, push를 감싼 git alias나 스크립트, 실제 Windows 세션.

C에 있던 "실패 테스트를 먼저 쓰는 턴"용 우회는 넣지 않고, 사용자만 켤 수 있는 형태로 [ROADMAP](ROADMAP.md)에 씨앗으로 남겼습니다. Python 브리지 같은 저장소별 검사는 `extra` 단계로 넣습니다.

## 7. 도입 계획: 개인 4주, 그다음 팀

목표는 문법 암기가 아니라 **AI가 쓴 Rust를 판정하는 눈**을 기르면서 쓸모 있는 결과물을 남기는 것입니다(판단).

| 시점 | 할 일 | 완료 기준 |
|---|---|---|
| 1주차 | 소유권·빌림·수명을 *예측하며* 익히기. 코드를 바꾸기 전에 컴파일 결과를 먼저 말해 보고 맞춰 봅니다. The Rust Book 4장·10장을 에이전트 설명과 함께. 일부러 `Box::leak`, 불필요한 `clone`을 넣고 리뷰어가 잡는지 봅니다. | 빌림 에러를 보고 원인과 해결안 두 가지를 스스로 말한다 |
| 2주차 | 개인 도구 하나를 하네스 위에서. 셸·Python 스크립트 하나를 CLI로 옮기거나 `rmcp`로 개인 MCP 서버를 만듭니다. 타입 설계는 직접, 구현은 에이전트. | `fsmap verify --mode full` 통과, 매일 실제로 쓴다 |
| 3주차 | 핫스팟 하나를 숫자로 증명. 프로파일링으로 고른 Python·Node 함수 하나를 PyO3/napi-rs로 옮기고, 결과 일치 단언과 전후 측정을 함께 둡니다. | 같은 결과, 측정된 개선, 되돌리는 방법이 문서에 있다 |
| 4주차 | 동시성 기초와 리뷰하는 눈. `Send`/`Sync`, 스레드, 필요하면 tokio. 에이전트의 변경을 리뷰어 점검 목록으로 직접 리뷰하고 서브에이전트 결과와 비교합니다. 회고는 체감이 아니라 기록(소요 시간, 막힌 지점, `fsmap hook stats`)으로. | 회사 적용을 §4 기준으로 판단할 수 있다 |
| 분기 | 사내 배포용 단일 바이너리 하나 + 이 하네스를 템플릿으로 | 템플릿 재사용 2건 이상 |
| 팀 | `unsafe` 정책, 크레이트 허용 목록(cargo-deny), "서드파티 크레이트 먼저, C++→Rust 단방향 FFI"로 시작. Chromium의 2023년 출발점이었고, 지금은 1st-party Rust와 양방향 interop까지 넓어졌습니다. | 리뷰 가이드 문서화 |

## 8. 실제로 해 본 것

### 8.1 이 저장소(fsmap)

수치는 이 저장소 작업 세션의 도구 실행 결과입니다(4코어 클라우드 컨테이너, rustc 1.97).

- **규모**: Rust 코드 12,454줄(테스트 포함, 주석·빈 줄 제외)과 뷰어 JavaScript 1,021줄입니다. fsmap이 자기 자신을 잰 값입니다(`fsmap scan`, 2026-10-29). `unsafe`는 0줄이며 lint로 금지했습니다.
- **성능**(2026-10-28):
  - ripgrep 저장소 분석(2,241커밋 전체 이력, import 그래프, 핫스팟)에 0.23초가 걸렸습니다(5회 중앙값).
  - `/usr` 93k 노드는 디렉터리 순회 0.14초, 피크 RSS 88MB였습니다.
  - 같은 `/usr`의 텍스트 456MiB 읽기는 따뜻한 캐시에서 1.6초, 콜드 캐시에서 10.8초(I/O 바운드)였습니다.
- **컴파일러가 잡은 것**: 반복 가능한 빌림 충돌(E0502) 3건(그중 하나는 `&mut` 인덱싱 중의 불변 빌림)과 불안정 API 사용 시도(E0658) 1건. 모두 실행 전에 막혔습니다.
- **컴파일러가 못 잡은 것**: 이력 분석 기간을 "현재 시각 기준 2년"으로 잡은 설계 결함. 2년 넘게 커밋이 없는 저장소는 이력이 통째로 사라졌습니다. git 픽스처 위에서 바이너리를 직접 돌리는 통합 테스트가 잡았고, 기간을 "저장소의 최신 커밋 기준"으로 바꿨습니다(D-09).
- **실데이터 대조**: 실제 OSS 저장소(ripgrep, flask, hono, redis)에 돌려 결과를 원본과 하나씩 맞췄습니다. flask에서 처음 보고된 15개 모듈 순환은 `TYPE_CHECKING` 블록 안의 import였습니다. 런타임 순환이 아닌 오탐이었고, 지연 import를 순환 판정에서 빼도록 고쳤습니다.
- **독립 리뷰 여섯 번**: 작성자와 컨텍스트를 공유하지 않는 에이전트에게 맡겼습니다.
  - 코드 리뷰(D-13)는 신뢰할 수 없는 저장소의 git filter 설정이 스캔 중 실행될 수 있다는 보안 결함을 찾았습니다. 컴파일러도, 테스트도, 작성자도 놓친 것입니다.
  - 문서 리뷰(D-14)는 문서와 동작이 어긋난 곳 26군데를 찾았고, 그중 몇 곳은 코드가 틀린 경우였습니다. 그 수정 커밋을 다시 리뷰에 맡기자 수정이 만든 회귀가 나왔습니다. **고친 코드도 다시 검토받아야 합니다.**
  - 하네스 설계 리뷰(D-15)는 차단 3건, 주요 8건을 냈습니다. 그중 하나가 위의 `.cargo/config.toml` 우회였고, 다른 하나는 submodule의 filter 드라이버가 실행되는 경로였습니다. 후자는 하네스 이전부터 `brief --diff`에 있던 구멍이라 원래 PR에서 함께 고쳤습니다.
  - 하네스 구현 리뷰(D-15)는 차단 2건, 주요 6건을 냈습니다(§6). 그중 하나는 문서였습니다. 안내서와 결정 기록이 "보호 장치마다 변형 검사를 거쳤다", "조용히 실패하지 않는다"고 적고 있었지만 사실이 아니었습니다. **작성자가 쓴 '검증 완료'도 검증 대상입니다.**
- **하네스를 만들며 배운 것**:
  - procps의 `kill -KILL -<pgid>`는 아무것도 죽이지 않았습니다. `kill -s KILL -- -<pgid>`로 고쳤습니다(단위 테스트가 잡음).
  - 훅 테스트 두 개는 *엉뚱한 이유로* 통과하고 있었습니다. 훅 자신의 캐시 디렉터리와 생성된 `Cargo.lock`이 지문을 바꿨기 때문입니다.
  - 그래서 보호 장치를 하나씩 제거한 변형을 만들어, 각 테스트가 실제로 실패하는지 확인했습니다. 구현 리뷰 뒤에 21개로 늘려 다시 돌렸습니다. 그중 하나는 장치를 빼도 테스트가 통과했습니다. 테스트에 쓴 설정이 다른 단계까지 깨뜨려, 정작 확인하려던 경우를 만들지 못하고 있었습니다. 그래서 다른 단계를 건드리지 않는 설정으로 바꿨습니다. 테스트가 통과한다는 것과 무언가를 증명한다는 것은 다릅니다.
- **실제 세션에서**: 훅을 만든 Claude Code 클라우드 세션 안에서 설정 파일이 생기자마자 훅이 적용됐습니다. 편집 직후 `cargo check`가 돌았고(10회 중앙값 1.1초), 리팩터링 중에는 호출부 두 곳을 깨뜨린 편집을 바로 막아 알려줬습니다. 자동 압축 때의 세션 시작 훅은 기준점을 덮어쓰지 않았습니다. 첫 턴 종료 때는 리뷰 서브에이전트가 백그라운드에서 돌고 있어 Stop 훅이 게이트를 설계대로 미뤘습니다. 실제 턴 종료에서 게이트가 끝까지 돈 기록은 이 글을 쓸 때 아직 없었습니다.

### 8.2 C 작업(rust-ai-harness)의 기록

다른 환경(그 작업의 보고: x86_64 2 vCPU, rustc 1.99.1, PyO3 0.30.1, CPython 3.13.18)에서 잰 것입니다. 이 저장소에서 다시 재현한 항목은 따로 표시했습니다.

- **누수는 컴파일을 통과합니다.** `'static` 수명을 맞추려고 쓴 `Box::leak`이 컴파일과 테스트를 통과했고, 커밋 전 자체 검토에서야 발견돼 `Cow`로 고쳤습니다. 안전한 Rust도 누수는 허용합니다.
- **추론이 틀렸던 사례.** "PyO3 매크로가 unsafe를 생성하니 `forbid(unsafe_code)`를 낮춰야 한다"고 추론했는데, 실제로 빌드해 보니 forbid로도 통과했고 직접 쓴 unsafe만 정확히 거부됐습니다.
- **clippy 도움말과 `exclude` glob.** clippy 도움말이 `#[allow]`를 권한다는 것, workspace `exclude`가 glob을 처리하지 않는다는 것은 여기서도 재현했습니다(cargo·clippy 1.97).
- **적대적 리뷰가 찾은 구멍들.** 턴 중 커밋 우회, 해시 도구가 없으면 게이트가 꺼짐, Python 브리지가 로컬 검사 밖에 있음, `--config`로 임의 명령 실행. 고친 뒤 다시 리뷰하자 수정이 만든 회귀와 아무것도 증명하지 않는 훅 테스트가 나왔고, 마지막 리뷰에서 빈 저장소 첫 커밋 우회가 더 나왔습니다. 위의 fsmap 경험과 같은 패턴입니다.
- **브리지 벤치마크.** 30만 줄 logfmt 로그의 `level` 집계에서 실행별 결과는 Python 루프 2.05~2.26초, Python 정규식 1.15~1.42초, Rust 확장 131~170ms였습니다. 정규식 대비 7.2~9.8배입니다. 실행 6번의 범위이고, 세 구현의 결과가 같은지 단언한 뒤 쟀습니다. 여기서는 재현하지 않았으니 자기 환경에서 다시 재세요.

**교훈**: 컴파일러는 *형태*의 오류를 거의 다 잡지만, *의미*의 오류는 테스트와 실데이터 대조의 몫입니다. 그리고 AI가 쓴 코드는 AI에게 다시 검토시키되, **반드시 컨텍스트를 끊고 적대적으로** 시키세요. 고친 코드와 테스트 자신도 그 대상입니다.

## 9. 반론과 남는 위험

- **"AI가 다 써주면 언어는 상관없다."** 쓰기만 놓고 보면 맞습니다. 하지만 읽고 판정하는 비용은 언어마다 다르고, AI가 많이 쓸수록 그 차이가 커집니다(판단). 팀이 이미 강한 스택에서 얻는 이득이 크다면 바꿀 이유는 약합니다.
- **Rust는 AI에게도 어렵습니다.** 최신 API, 저장소 구조, C→Rust 번역에서 정답률이 눈에 띄게 낮고(§1), 벤치마크마다 평가가 갈립니다(SWE-bench Multilingual에서는 언어 중 최고, Multi-SWE-bench에서는 중간). 컴파일 시간 때문에 반복 한 번이 길어져, 검증이 싸지는 만큼 작성이 비싸질 수 있습니다(판단).
- **체감과 실제는 다릅니다.**
  - METR의 2025년 초 실험(숙련 개발자 16명, 자기 저장소)에서 AI를 쓴 작업은 19% 더 오래 걸렸는데, 참가자들은 20% 빨라졌다고 느꼈습니다.
  - 2026-02 후속 발표에서는 같은 참가자 10명이 18%, 새 참가자 47명이 4% 빨라진 것으로 추정됐지만 두 신뢰구간 모두 0을 포함합니다. METR은 지금은 더 빨라졌을 가능성이 높다고 보면서도, AI 없이 일하기를 거부하는 개발자가 늘어 제대로 재기 어렵다고 밝혔습니다.
  - 그래서 회고는 기록으로 합니다. 하네스의 효과도 아직 측정 전입니다(`fsmap hook stats`로 차단·오탐·추가 시간을 모으는 중).
- **이해 부채.** 에이전트가 쓴 Rust가 아무도 깊이 이해하지 못한 채 쌓이면 장애 때 고칠 사람이 없습니다. 계획의 중심이 판정하는 눈인 이유입니다.
- **복잡도와 과장.** 설문 응답자의 41.6%가 언어가 너무 복잡해지는 것을 걱정했습니다. 고급 트레이트·매크로·async는 필요해질 때까지 규칙으로 막는 편이 낫습니다. "2030년까지 마이크로소프트의 C/C++를 없앤다"는 엔지니어 한 명의 연구 목표였고 공개적으로 정정됐습니다.

## 10. 초안(Gemini) 아이디어에 대한 교정

| 초안의 주장 | 교정 |
|---|---|
| Chromium은 gclient/depot_tools 없이는 받기 어렵다 | **빌드**에는 맞습니다. **분석**만 하려면 `git clone --filter=blob:none` + sparse-checkout으로 충분합니다. fsmap은 부분 클론을 감지하면 이름 변경을 객체 id가 같은 경우(`-M100%`)로만 추적해서, 이력 분석 중에 blob을 받지 않습니다(D-08, D-13). |
| AST 파서로 의존성을 시각화한다 | AST는 *추출*만 해 줍니다. 어려운 부분은 *해석*입니다. `use crate::a::b`, `from ..x import y`, tsconfig 경로 별칭, 워크스페이스 패키지가 어느 파일인지 찾아야 합니다. fsmap은 해석에 공을 들였고, tree-sitter는 추출기 교체 경로로 남겼습니다(D-04). |
| 5,100만 줄이 유지되는 비결은 모듈화와 의존성 관리 → 시각화 도구 | 시각화는 출발점일 뿐입니다. Chromium을 지탱하는 것은 디렉터리별 `DEPS` 파일의 include 규칙과 이를 검사하는 checkdeps, 필수 코드 리뷰와 OWNERS 같은 **래칫**입니다. fsmap의 `insights --baseline --fail-on`이 이 아이디어의 경량판입니다. *새로* 생긴 순환·문제만 CI에서 막습니다. |
| AI 에이전트용 경량 임베디드 브라우저 | Playwright MCP 같은 CDP·Playwright 기반 도구가 이미 그 자리를 채우고 있습니다. Chromium 래퍼를 직접 유지하면 차별점은 작고 유지비는 큽니다(판단). 꼭 한다면 Rust CDP 클라이언트(chromiumoxide)로 자동화 계층만 만드세요. |

## 11. 다음 실험 후보

- **하네스 효과 측정**: 실제 세션 여러 개의 `fsmap hook stats`로 차단, 오탐, 추가 시간, 우회를 모읍니다. 효과를 주장하기 전에 먼저 할 일입니다.
- **fsmap MCP 서버**(`rmcp`): 에이전트가 "이 파일과 같이 바뀌는 파일은?"을 도구 호출로 묻게 합니다.
- **대형 워크스페이스용 게이트**: 바뀐 패키지와 그 역의존 패키지만 테스트합니다.
- **Chromium 실측**: 부분 클론 + `fsmap report`. 이 도구가 원래 영감을 받은 대상에 돌려 보는 대형 모노레포 스트레스 테스트입니다.
- **WASM 빌드, PyO3 바인딩**: 업로드 없는 브라우저 맵, 노트북의 `fsmap.scan(path)`.

자세한 씨앗 목록은 [ROADMAP.md](ROADMAP.md)에 있습니다.
